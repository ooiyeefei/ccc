# pitch-package

The **step-back orchestrator** for pitching as a person: given an audience (hackathon judges, VCs, customers) and a time slot, it budgets the slot, decides what to build or reuse, and composes the `pitch-deck`, `demo-video`, and `pitch-craft` skills into one rehearsed package.

Four phases, two governing rules:

1. **Interview before you build** - audience, slot, inventory of what exists, demo mode (live vs recorded), speakers, venue constraints. No artifacts until the brief is confirmed.
2. **Budget the slot first** - the explicit budget line (spoken + demo + transitions) decides scope before any writing.
3. **Compose** - audience lens (judges: proof + rubric fit; VC: market + what compounds + the ask; customer: their pain + pilot ask), then gap-fill via the other skills with one shared throughline.
4. **Rehearse and ship** - stitch plan, timed read-through with named trims, Q&A appendix + honest-defense brief, day-of checklist (local copies, venue test, fallback ladder).

The framing that holds it together: **the demo is the proof, the deck is the setup.**

## Use this, not that

- **Start here when preparing a WHOLE pitch** for an audience and a time slot - it interviews, budgets, then routes work to the other three skills.
- Only one artifact missing? Skip the orchestrator: `pitch-craft` (words), `demo-video` (footage), `pitch-deck` (slides).
- Part of the pitch suite: decision guide in [skills/README.md](../README.md#the-pitch-suite---when-to-use-what).
